# 服务端三方合并并通过短暂写维护切换

多设备可以离线编辑同一套色板，因此我们决定由 `2048-game-api` 使用客户端声明的共同 revision、客户端完整规范化色板和服务端当前 revision 执行权威三方合并。互不重叠的最小编辑单元自动合并；同一单元产生不同结果时保留服务端当前色板，并把后到修改创建为新的冲突副本。迁移到新权威模型时采用短暂的色板写入维护窗口，不长期双写旧整库文档和新逐套记录。

## Considered Options

- **客户端合并并覆盖服务器**：不同设备可能得到不同结果，且客户端无法原子执行容量、删除标记和幂等约束。
- **最后写入覆盖**：简单但会静默丢失先提交设备的修改。
- **长期双写旧表和新表**：会制造两个权威来源，部分失败时难以证明一致和安全回滚。
- **服务端合并 + 短暂维护切换**：实现成本更高，但权威单一、无损保留并发修改，切换边界可审计。

## Consequences

- 服务器保存最近 100 个版本与最近 180 天内全部版本的并集；当前版本和删除标记始终保留。
- 客户端只提交稳定 palette ID、base revision、完整最终内容和幂等 operation ID。
- 共同版本不存在时，相同内容视为已同步；不同内容自动保留为冲突副本，满库时成为本地待上传色板。
- 迁移期间先扩展、回填和影子对账，再暂停色板写入完成最终增量迁移；维护窗口内必须先关闭 legacy PUT 并证明旧写不可能成功，随后才能开启 V2 write，任何时刻只有一个可写权威。
- 切换后的回滚只关闭写能力并回滚代码，不删除新数据，也不重新开放旧整库 PUT。
