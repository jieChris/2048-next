# 55接力模式可行性与安全评估（2026-04-04）

## 1. 结论
55接力模式可做，但必须按“协作状态机”建设，不能按“共享文件”思路实现。

可行前提：
- 有唯一真源（数据库）
- 有租约锁（同一时刻仅一人持档）
- 有版本控制（防止覆盖写）
- 有审计日志（可追踪、可回滚）

不建议方案：
- 仅用 COS/R2 作为唯一状态真源
- 固定“10分钟刷新一次”作为同步机制

## 2. 目标边界
本期建议只做最小可用版本（MVP）：
- 单档接力（一个存档，一个持有者）
- 接档确认 + 交档确认
- 持有超时自动释放
- 全站可见状态（谁在持有、最后更新时间、当前版本）

暂不纳入：
- 多人并行编辑同一档
- 多档编排与复杂赛制联动

## 3. 存储与服务架构
推荐三层：
1. 数据库（真源）
- relay_case（档案主表）
- relay_lock（租约锁）
- relay_event（事件流）
- relay_audit（审计）

2. 对象存储（大对象）
- 快照文件
- 回放文件
- 导出包/附件

3. 协调层（锁服务）
- CAS抢锁
- 心跳续租
- 超时回收

## 4. 锁与并发模型
### 4.1 租约锁字段
- case_id
- holder_user_id
- lease_version
- lease_expires_at
- last_heartbeat_at
- state_version

### 4.2 关键规则
- 接档：必须原子检查“当前无有效持有者”
- 操作提交：必须同时校验“持有者身份 + state_version”
- 交档：仅当前持有者可发起，目标用户确认后生效
- 超时：超过租约自动释放，允许他人接档

### 4.3 冲突处理
- 优先有效持有者
- 版本不一致即拒绝写入并返回冲突提示
- 不允许“最后写入覆盖一切”

## 5. “10分钟更新一次”替代策略
固定10分钟刷新不适合接力场景，建议改为：

1. 写操作实时同步（必须）
- 接档、交档、提交、放弃、释放锁：实时写数据库

2. 列表/详情近实时刷新
- 优先 SSE/WebSocket 推送
- 无推送能力时降级为 5~15 秒短轮询

3. 心跳机制
- 持有者每10~15秒发送心跳
- 心跳断开后按租约超时自动回收

4. 降级策略
- 推送失效 => 自动切短轮询
- 心跳失效 => 自动回收锁
- 审计写入失败 => 主状态成功后异步补写

## 6. 安全基线（最小可上线）
1. 鉴权
- 所有接档/交档/提交接口必须登录态

2. 权限校验
- 仅持有者可提交
- 仅持有者可发起交档
- 管理员可强制释放

3. 频控
- 用户维度 + IP维度限流
- 抢档、交档、提交接口单独限速

4. 审计
- 记录操作者、时间、动作、前后版本、结果

5. 防重放
- 关键写接口使用幂等键/操作ID
- 重复请求不重复生效

6. 异常治理
- 高频失败或越权行为进入临时封禁/冷却

## 7. 审计与追踪字段
建议每条关键事件记录：
- case_id
- event_id
- actor_user_id
- action
- state_version_before
- state_version_after
- timestamp
- result
- ip_hash
- user_agent_hash

## 8. 落地顺序（建议）
阶段1：基础模型
- 建表（case/lock/event/audit）
- 实现接档、提交、放弃、释放

阶段2：实时能力
- 心跳续租
- 列表短轮询
- 详情推送（SSE优先）

阶段3：风控与运维
- 频控与异常封禁
- 审计检索与问题回放
- 管理员恢复工具

## 9. 风险清单
- 仅靠对象存储会导致并发冲突难以控制
- 无锁或弱锁会造成“双持有者”
- 无版本控制会导致覆盖写和数据丢失
- 无审计会导致问题不可追责

## 10. 最终建议
上线MVP时坚持三条红线：
- 状态真源必须在数据库，不在对象存储
- 接档与提交必须走“锁 + 版本”双校验
- 同步策略必须近实时，不采用“10分钟固定刷新”
