## 调查记录

- 当前请求是复杂的全新移动前端规划，需要在 PRD 确认后补齐 `design.md` 和 `implement.md`，并由用户审阅后才能进入实现。
- 用户已确认接受 Capacitor，但最终产品必须使用 App 专属页面、入口和交互，不是线上网页壳或现有 Web 的简单移动适配。
- 当前 Web 的 legacy 脚本并非全部无效：`play` 清单仍主动加载 91 个脚本；同时审计明确阻止 56 个已退役 runtime 返回现代清单。App 基底不得把这套加载图整体复制过去。
- 现有后端与数据边界适合增加移动客户端；主要规划风险位于无 DOM 游戏核心、API 契约冻结、移动生命周期、安全存储、持久化 outbox 和 Android 发布链路。
- 用户确认首个公开版本只覆盖玩家核心产品；管理后台、接力工具、2K 监控、完整色板编辑和实验模式延后为独立模块。
- Capacitor App 的页面与静态资源随 APK/AAB 本地发布，不需要新增移动前端托管服务；在线产品能力继续复用现有 `2048-game-api`。
- 用户明确长期目标为 Web、Android App、微信小程序三端并存，共享同一后端、账号和云端业务数据；当前 Android 基底规划必须同时定义可供小程序复用的核心与契约边界。
- 代码扫描未发现 `openid`、`unionid`、微信登录或通用第三方身份映射模型；三端统一账号需要在后端新增平台身份到权威用户 ID 的映射，而不是为小程序复制用户表。
- 用户确定先做 Android App，小程序延后；游客只可游玩一个 4×4 经典玩法，其他模式在开始前要求登录。
- 当前模式目录把无撤回玩法命名为“标准版 4×4”，把可撤回玩法命名为“经典版 4×4”；已将游客具体模式键列为产品问题，未擅自按口语含义推断。
- App 首页信息架构开始收敛。现有 Web 首页同时承载对局、用户、公告、统计、新游戏、回放导出、练习盘、模式、设置、计分和计时信息，移动端不直接继承这一入口密度；当前最高优先级产品决策是首页采用“快速开局页”还是“综合大厅”。
