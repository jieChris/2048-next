# 第三方平台游戏记录批量导入

## Goal

为管理员后台增加一个面向单个目标玩家的第三方记录导入模块。管理员可上传一个单文件或一个压缩包；系统只接受已有适配器能够解析、且可由服务端回放验证器验证的完整终局记录。成功记录进入玩家历史，保留来源平台标记，但不进入排行榜、正式统计、Rating 或基于正式成绩的成就计算。

## Background and Confirmed Facts

- Next 管理后台已经有独立“成绩补录”模块，但当前只处理一条原生回放，并将其作为 `official_v1` 管理员补录写入：`src/pages/admin-page.ts:756-809`。
- Game API 已有批量导入核心 `importUserReplayRecords()`，能够逐条预校验、去重、部分成功并返回明细：`scripts/import-user-replay-records.ts:432-470`。
- 现有导入核心默认写入 `record_era = beta`，且不主动刷新排行榜；管理员正式补录路由才显式切换为 `official_v1` 并执行排行榜/成就钩子：`scripts/import-user-replay-records.ts:340-422`、`src/server/app.ts:6269-6331`。
- 部分 canonical leaderboard 维护脚本仍把 `source IN ('admin', 'migration')` 当作竞争来源且未同时筛 era；因此第三方记录不能使用 `migration` 来源，否则未来维护重跑存在污染风险：`scripts/backfill-canonical-leaderboard.ts:352-390`、`scripts/gate-canonical-leaderboard-indexes.ts:21-24,97-102`。
- 玩家历史接口会返回所有 era 的记录，而正式统计和排行榜只读取 `official_v1`；前端已有“内测成绩”只读标记及对应 Smoke：`src/server/app.ts:3238-3310`、`tests/smoke/pages-user-profile-title.smoke.spec.ts:1168-1315`。
- 当前服务端验证器只接受 `REPLAY_v1RPL_B64_` 原生回放格式。
- Next 回放页已经实现 2048Verse、新 VRS 等兼容解析，且版本公告明确声明与 2048Verse 通用：`src/bootstrap/game-manager-replay-helpers-runtime.ts:516-576,804-876`、`js/announcement_records.js:189-191`。这些解析目前只在浏览器 GameManager 运行时中，尚未形成可供 Game API 复用的纯服务端适配器。
- 当前前后端均没有 ZIP 解析依赖。

## Requirements

### R1. 独立入口

- 在管理员后台“成绩补录”区域提供“第三方记录导入”独立工作区，不改变现有正式成绩补录语义。
- 每次导入必须指定一个目标玩家。

### R2. 输入与预览

- 接受一个单文件，或一个 ZIP 压缩包。
- 导入前必须先执行 dry-run，展示总数、可导入、重复、格式不支持、验证失败等逐项结果。
- 页面完成当前文件的 dry-run 后方可确认；文件或目标玩家变化时预览失效。提交时服务端重新解析、验证与去重，只写入当次仍有效且未重复的记录。

### R3. 适配与验证

- 首批只适配以下格式：
  - 2048Verse `replay_` 文本。
  - 新 VRS `.vrs/.txt`，覆盖现有代码已支持的 2x4、3x3、3x4、4x4 棋盘。
  - Next 原生 RPL1 `.rpl/.json`。
  - ZIP 仅作为上述文件的批量容器，不作为新的回放格式。
- 原始文件必须先由明确的平台适配器识别；无法识别或适配器版本不支持的文件不得猜测写入。
- 适配器输出必须进入现有服务端 `verifyReplaySubmission()` 完整终局验证；上传文件里的分数、盘面和用时不能直接作为可信结果。
- 只有包含完整终局回放、且可无损转换为原生 RPL1 的记录才允许导入；仅有分数、截图、最终盘面或缺少生成方块序列的摘要必须拒绝。

### R4. 非竞争记录

- 成功记录写入玩家历史，但必须使用非正式 era，永不刷新 `leaderboard_best`。
- 不计入正式统计、Rating、排行榜和正式成绩成就。
- 记录在玩家历史中只读，沿用现有 beta 记录的保护边界。

### R5. 来源标记与审计

- 每条记录保留规范化平台 ID、展示名称、适配器版本、原文件名和管理员导入原因。
- 玩家历史显示“第三方 · 平台名”标记；管理员记录页可看到同一来源信息。
- 每次预览和正式导入都需要超级管理员鉴权；正式导入写审计日志和批次摘要。

### R6. 安全与幂等

- 首版限制为：上传体积不超过 8 MiB、ZIP 条目不超过 500 个、单个候选文件不超过 2 MiB、累计解压体积不超过 32 MiB、单条目压缩比不超过 100:1。
- 拒绝绝对路径、父目录穿越、嵌套压缩包、加密 ZIP、符号链接语义及目录条目之外的非普通文件。
- 继续使用 replay fingerprint 和 client record ID 去重；同一批次重复项不得重复写入。
- 单个文件的格式或回放验证失败不应阻止其他有效文件预览；容器结构违规或命中安全上限时整包拒绝。最终写入结果必须逐项返回。

## Acceptance Criteria

1. 管理员可为一个用户上传首批支持格式的单文件或 ZIP，随后看到逐项 dry-run 结果；受支持范围准确限制为 2048Verse `replay_`、新 VRS 2x4/3x3/3x4/4x4、Next 原生 RPL1 `.rpl/.json`。
2. 受支持且通过服务端完整终局验证的记录可批量写入；数据库重复、批内重复或无效项被跳过并给出明确原因。
3. 导入记录出现在该玩家历史中，并显示“第三方 · 平台名”标记及可用回放。
4. 导入前后排行榜、正式统计、Rating 和正式成绩成就均不发生变化。
5. 未登录或非超级管理员无法调用预览和提交接口。
6. 超限、Zip Slip、嵌套/加密压缩包、未知格式和不完整回放均被拒绝，且不会产生半条记录或孤立回放对象。
7. 正式导入留下批次摘要和可追溯到管理员、目标玩家、来源文件的审计记录。
8. OpenAPI、Game API 单元测试、Next 管理后台单元/Smoke、玩家历史 Smoke 覆盖上述契约。

## Out of Scope

- 通过管理员界面手工修改解析出的分数、盘面、步数或用时。
- 将第三方记录升级为正式成绩或参与排行榜。
- 一个压缩包自动分配给多个本站用户。
- 未取得样例或未实现适配器的平台格式。
- 旧 v9 `.rpl` 等未纳入本次确认范围的兼容格式；取得真实样例并单独验证后再增加适配器。
- RAR、7z、tar 等非 ZIP 压缩格式。
- 修改或部署 `2048-ranked`。
