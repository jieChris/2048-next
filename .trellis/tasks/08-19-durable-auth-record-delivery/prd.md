# 持久登录与本地成绩可靠投递 PRD

## 文档状态

- 阶段：用户已批准，实施中
- 范围：`2048-next` 前端与 `2048-game-api` 后端的跨仓库协作
- 产品术语：使用“具备排行榜的模式”“排行榜记录”“排行榜资格”，不使用“排位模式”描述产品
- 当前授权：允许在隔离分支修改产品代码、增加向前兼容迁移并执行本地专项验证；未经另行授权不推送、不部署、不写生产数据

## 1. 问题陈述

玩家结束一局游戏后，记录有时只存在浏览器本地历史，服务器没有收到或没有完成入库。因此玩家在账号历史、排行榜和回放列表中找不到本局成绩，只能人工补录。当前上传链路存在几个相互放大的失效点：

1. 终局 payload 主要依赖 `localStorage` 待上传队列，容量有限、写入失败不显式报告，并且队列会静默截断。
2. 认证令牌只有约 30 天有效期，前端没有真正的设备会话恢复；令牌失效时部分错误路径会连同待上传成绩一起清理。
3. 网络错误、服务端暂时不可用、请求体过大和认证失效没有统一分类，某些可恢复错误会被当成永久失败。
4. 本地历史没有完整的同步状态、服务器记录 ID、重试时间和错误诊断，玩家无法知道“本地保存”与“服务器已确认”的区别，也没有可靠的自助补传入口。
5. `5×5` 或更长对局的 RPL1 回放可能超过现有单请求约 2 MiB 限制；只增加重试次数不能解决请求体上限。
6. 服务器已有回放验算和幂等索引，但重复检测、排行榜会话关联和历史资格字段的处理必须保持原子且兼容，不能通过隐藏或删除其他玩家成绩来“修复”。

这不是单纯的“再发一次请求”问题，而是终局证据、认证、传输、服务端验算和用户可见状态没有形成闭环。

## 2. 产品目标与成功标准

### 2.1 持久登录目标

用户成功登录一次后，在以下情况之外不应因为时间经过、刷新、关闭并重新打开页面而被要求重新登录：

- 用户主动退出当前设备；
- 用户主动清除浏览器站点数据；
- 用户修改密码、删除账号或执行安全操作导致会话被撤销；
- 服务端明确撤销该设备会话或账号被停用。

“至少每 30 天打开一次网站”不是本产品目标。短期访问令牌可以过期，但设备会话必须能够在页面启动时自动恢复。

### 2.2 成绩投递目标

- 每个已结束且本地证据完整的有效对局，至少有一次到达服务端的机会。
- 上传成功由服务端返回的 `server_record_id` 确认，不以“请求已发出”或“本地已显示”作为成功。
- 同一局重复上传只能得到同一条服务器记录，不产生重复成绩。
- 任何可恢复失败都保留本地证据，自动重试或允许用户手动补传。
- 明确不可验证的记录也保留在本地，展示原因并允许导出；不得静默删除。
- 服务器不得因一个目标方块的速度异常而隐藏整条记录、回放、分数或其他目标的指标。

### 2.3 大回放目标

- 普通回放继续使用现有 RPL1 和单请求上传路径。
- 超过服务端安全阈值的回放自动切换为分块、可断点续传路径。
- 分块上传完成后由服务端校验整体哈希和 RPL1 语义，再原子创建成绩。

### 2.4 可观测性目标

运营和开发可以区分：本地落盘失败、等待认证、网络重试、服务端拒绝、请求体过大、幂等命中和最终成功；不能只看到一个笼统的“上传失败”。

## 3. 用户故事

1. 作为已登录玩家，我希望刷新或重新打开页面后仍保持登录，以便继续游戏而不用重复输入密码。
2. 作为已登录玩家，我希望短期访问令牌过期时页面自动恢复会话，以便正常提交成绩。
3. 作为玩家，我希望网络断开时游戏结束记录仍保存在本地，以便恢复网络后自动上传。
4. 作为玩家，我希望在历史页看到每条记录是“已同步、等待认证、重试中、需处理还是已验证失败”，以便知道成绩是否真的进入账号。
5. 作为已登录玩家，我希望点击“检查并补传”只上传本地生成且尚未同步的记录，以便自行找回漏传成绩。
6. 作为游客，我希望记录先保存在本地；之后登录账号时，系统能在明确确认归属后将这些记录加入上传队列。
7. 作为切换账号的玩家，我希望甲账号的待上传记录不会被误传给乙账号，也不会因切换账号被删除。
8. 作为主动退出的玩家，我希望退出只撤销当前设备会话，同时保留本地成绩证据，之后重新登录仍可补传。
9. 作为修改密码的玩家，我希望旧设备会话被撤销，但本地记录不会丢失。
10. 作为玩家，我希望上传重复请求不会产生重复排行榜成绩。
11. 作为玩家，我希望 `5×5` 超长回放可以继续上传，而不是因为单次请求过大而永久失败。
12. 作为玩家，我希望浏览器存储空间不足时得到明确提示和导出建议，而不是看到一条已经消失的历史记录。
13. 作为玩家，我希望服务端拒绝某个速度指标时，普通分数、回放和其他目标仍然可见。
14. 作为玩家，我希望旧版本生成的本地历史仍可读取并进入兼容上传流程。
15. 作为运营人员，我希望看到上传失败的结构化原因和重试次数，以便定位真实故障而不是要求玩家人工截图。
16. 作为开发人员，我希望前端只负责本地状态和 API 调用，所有账号、排行榜资格、回放验算和数据库写入仍由 `2048-game-api` 权威处理。
17. 作为开发人员，我希望部署新版本或回滚时不需要删除现有玩家记录，也不需要重写回放格式。
18. 作为管理员，我希望在现有后台看到服务器已经观测到的投递健康数据，以便区分认证失败、服务异常、请求超限和幂等命中。
19. 作为管理员，我希望在用户详情中查看并撤销设备会话，以便处理丢失设备或账号安全事件。
20. 作为管理员，我希望在记录详情中看到 `client_record_id`、回放指纹、验证版本、投递结果和目标级资格，以便先诊断再决定是否需要人工补录。
21. 作为管理员，我希望发布或迁移前执行只读对账，以便任何记录数、玩家数或排行榜可见性异常下降都能阻止发布。

## 4. 术语与状态定义

### 4.1 记录证据

“本地可信文件”表示由本应用保存或导出的完整记录信封，包含模式、分数、终局盘面、`client_record_id`、RPL1 回放以及可用的排行榜会话凭证。它不是服务器签名，不能绕过服务端验算；手工修改的文件仍必须被服务端拒绝或降级。

### 4.2 本地同步状态

```text
active
  └─ 终局后本地提交成功 → finalized_local → pending
                                      ├─ 上传成功 → synced
                                      ├─ 认证不可用 → waiting_auth
                                      ├─ 暂时错误 → retry_wait
                                      ├─ 需要用户处理 → needs_action
                                      └─ 服务端明确无法验证 → invalid
```

- `active`：仍在进行的对局，不可提交为终局成绩。
- `finalized_local`：终局信封已完整写入 IndexedDB，并完成读回校验。
- `pending`：等待首次或下一次网络提交。
- `uploading`：内存中的互斥状态，不作为唯一持久状态；刷新后按 `pending` 恢复。
- `synced`：服务端返回成功和 `server_record_id`。
- `waiting_auth`：需要恢复或重新登录，不清理记录。
- `retry_wait`：按退避时间等待网络/服务恢复。
- `needs_action`：例如会话不匹配、请求体超限且分块不可用，需要玩家操作或升级客户端。
- `invalid`：服务端已明确说明回放/数据无法验证；证据仍保留。

## 5. 功能需求

### 5.1 认证与会话（AUTH）

**AUTH-01 登录建立设备会话**

- 登录、注册和密码重置成功后，服务端创建可撤销的设备会话。
- 浏览器收到 `HttpOnly`、`Secure`、适当 `SameSite` 的持久 Cookie；Cookie 不可被脚本读取。
- 同时返回短期访问令牌供当前页面内存中的 API 请求使用。
- 访问令牌不再作为长期凭证写入 `localStorage`。

**AUTH-02 页面启动恢复**

- 页面启动先调用会话恢复接口；成功后写入内存访问令牌、用户资料和过期时间。
- 恢复成功后立即扫描未同步本地记录。
- 恢复请求失败时不得删除待上传记录；只有服务端明确返回会话撤销/账号失效才显示未登录。

**AUTH-03 自动续签与单次重试**

- 访问令牌临近过期或 API 返回明确 `TOKEN_EXPIRED` 时，客户端只发起一次并发合并的恢复请求。
- 原请求在恢复成功后最多重试一次；避免无限循环。
- `400`、`403`（权限不足但非认证失效）、`409`、`429`、`5xx` 和网络断开不得被文本中的 `token` 字样误判为登出。

**AUTH-04 会话撤销语义**

- 主动退出只撤销当前设备会话并清除当前内存访问令牌。
- 修改密码、账号删除或安全中心的“退出所有设备”可以撤销全部设备会话。
- 撤销认证不得清除本地历史、终局信封或待上传队列。

**AUTH-05 旧客户端兼容**

- 旧 `localStorage` 令牌在仍有效时可一次性兑换为设备会话。
- 兑换成功后旧令牌不再作为长期登录依据；兑换失败只影响登录状态，不影响本地记录。

**AUTH-06 账号归属隔离**

- 每条本地记录保存 `owner_type`、`owner_user_id`（如有）和稳定 `owner_key`。
- 未登录记录不能自动发送给当前账号，除非用户在界面明确确认“将游客记录加入此账号”。
- 账号不匹配时进入 `needs_action`，不得删除或覆盖。

### 5.2 终局保存与发件箱（REC）

**REC-01 先落盘、后联网**

- 游戏结束时先构建完整终局信封并写入 IndexedDB。
- 写入后必须读回并校验 `client_record_id`、回放长度和 SHA-256（或等价稳定摘要）。
- 只有本地提交成功后才清理活动棋盘、退休当前排行榜会话或开始上传。
- `pagehide`/刷新路径可以使用 `keepalive`，但不能把网络请求当作唯一保存手段。

**REC-02 IndexedDB 为唯一发件箱**

- 完整回放只保存一份；上传队列只保存本地记录 ID、状态和重试元数据，不复制完整 payload。
- IndexedDB 版本升级必须保留旧记录，并为缺失字段填充兼容默认值。
- `localStorage` 中的旧待上传对象只做一次迁移源，迁移成功后不再作为权威队列。

**REC-03 自动扫描时机**

启动、会话恢复成功、重新登录、浏览器重新联网、打开历史页和用户点击“检查并补传”时扫描待同步记录。

**REC-04 手动补传入口**

- 历史页提供全局“检查并补传”按钮，并在每条可补传记录旁显示“上传/重试”。
- 按钮只处理本地已有的终局记录；不接受绕过历史存储的任意 JSON 直接写入排行榜。
- 上传过程中显示进度、当前状态和可重试错误；页面离开后队列仍保留。
- 成功后显示服务器记录 ID 或可跳转的账号历史入口；重复点击返回同一结果。

**REC-05 成功与失败清理规则**

- 只有服务端明确成功或用户主动删除本地记录时，才允许清理待同步状态。
- `401/419` 等认证失效保留记录并进入 `waiting_auth`。
- 网络、`429`、`5xx`、超时和暂时数据库不可用进入 `retry_wait`。
- 回放验算失败、模式不支持、数据结构损坏进入 `invalid` 或 `needs_action`，保留原始证据和错误代码。

**REC-06 幂等提交**

- 每条记录固定 `client_record_id`，重试不生成新的 ID。
- 服务端以现有 `(user_id, client_record_id)` 和 `(user_id, mode_key, replay_fingerprint)` 唯一约束为基础，重复提交返回同一 `server_record_id`。
- 同一回放先以普通记录保存、后补齐排行榜会话凭证时，服务端必须在事务内升级同一记录，而不是新增一条或拒绝后丢失。

**REC-07 目标级资格隔离**

- 速度资格按目标方块独立计算。
- 某个目标的时间异常只影响该目标的排行榜/成就资格；不改变记录、分数、回放、最大方块和其他目标。
- 缺少新资格字段的旧记录表示“未知/兼容”，不能直接解释为“不可信”，更不能批量隐藏历史成绩。

### 5.3 大回放（LARGE）

**LARGE-01 阈值协商**

- 普通上传前读取服务端返回的单请求上限或使用保守阈值。
- 低于阈值的记录沿用 `/api/records`。
- 超过阈值自动使用分块上传，不反复发送必然超限的完整请求。

**LARGE-02 分块可靠性**

- 创建上传任务时提交总字节数、整体哈希、`client_record_id`、模式和可用会话凭证。
- 每个分块带序号、长度和块哈希；重复上传同一块必须幂等。
- 网络中断后从已确认的最后一个块继续，不从头复制整个回放。
- 完成接口重新计算整体哈希并运行完整 RPL1 验算，成功后原子创建/升级记录。

**LARGE-03 失败回退**

- 分块接口不可用时，小记录仍使用普通接口；大记录进入 `needs_action` 并保留证据。
- 不通过截断回放、降低校验等级或删除回放来“适配”大小限制。

### 5.4 用户可见状态（UX）

- 账号区域显示“已登录（自动恢复）”或明确的未登录状态，不展示过期的本地令牌细节。
- 历史记录显示同步徽标：已同步、待上传、等待登录、重试中、需处理、验证失败。
- 错误文案给出下一步操作，例如“重新登录后重试”“恢复网络后重试”“导出文件联系客服”；不把所有错误统称为“登录失效”。
- 记录上传失败不弹出阻塞式无限重试；手动按钮和后台退避共用同一状态。
- 不新增“排位模式”文案；沿用现有模式名称和“排行榜资格”表述。

### 5.5 管理员最小运维能力（ADMIN）

本节只扩展现有 `2048-next` 管理后台及 `2048-game-api` Admin API，不新建后台产品，不修改独立的 `2048-ranked` 管理页面。

**ADMIN-01 投递健康概览**

- 在现有仪表盘或数据工具中展示服务器已经观测到的上传成功、重复幂等命中、认证失败、`413`、`429`、`5xx` 和分块任务状态。
- 支持按时间、模式、客户端版本和错误代码筛选。
- 必须明确说明：从未到达服务器的浏览器本地记录无法被后台统计；不得把服务器指标包装成“所有本地待上传数量”。

**ADMIN-02 设备会话管理**

- 用户详情展示设备会话的创建时间、最近使用时间、设备标签和有效/已撤销状态，不展示原始 Cookie 或 token。
- 支持撤销单个设备会话和撤销该用户全部设备会话，均要求确认、原因和审计。
- 现有“强制注销”调整为设备会话撤销语义，不得顺带删除该用户浏览器中的本地成绩。

**ADMIN-03 记录投递与验证详情**

- 记录列表/详情增加 `client_record_id`、回放指纹、来源版本、验证版本、幂等结果、服务器错误代码、分块任务状态和目标级速度资格。
- 管理员能区分“服务器未找到该记录”“重复命中”“认证失败”“回放无效”“会话冲突”和“超限等待分块”。
- 已存在的人工补录保留为最后手段，继续执行服务端预校验；分数、盘面、步数和时长不可编辑。

**ADMIN-04 审计和异常事件**

- 记录设备会话创建/使用/撤销、记录接收/重复命中/分块完成、用户自助补传、管理员补录及目标级资格变更。
- 审计日志不得保存完整访问令牌、设备 Cookie 或完整回放。

**ADMIN-05 只读对账门禁**

- 复用现有后台数据工具或发布脚本，提供迁移/发布前后的记录数、玩家数、模式榜单数、Top N 和目标级资格数量对比。
- 对账工具只读；出现未批准下降时阻断迁移或发布，不提供“一键隐藏”“批量 review”或任意 SQL 修复按钮。

**ADMIN-06 收紧危险操作**

- 现有“隐藏/恢复记录”仅用于有明确理由的内容治理，与上传状态、回放校验和速度资格完全分离。
- 缺少新字段、上传失败或单个目标速度异常都不能成为隐藏整条记录的默认原因。
- 不增加“管理员批量重试所有记录”“上传任意 JSON 直接获得排行榜资格”或“全量浏览器本地记录遥测”。

## 6. 验收标准

### 6.1 认证验收

1. 登录后关闭并重新打开页面，未清除站点数据且未撤销会话时，页面自动显示同一账号。
2. 将内存访问令牌模拟为过期，页面启动恢复成功，原 API 请求最多重试一次且不要求用户重新输入密码。
3. 恢复接口返回网络错误或 503 时，账号 UI 可以暂时显示“正在恢复/稍后重试”，本地待上传记录仍存在。
4. 服务端返回 `TOKEN_REVOKED`、账号停用或账号删除时，清除会话但保留所有本地记录。
5. 主动退出后当前 Cookie 被撤销；重新登录可恢复同一用户的待上传队列。
6. 两个账号切换时，记录不会跨账号自动提交。

### 6.2 成绩验收

7. 终局时中断网络或冻结 `/api/records` 请求，刷新页面后本地历史仍有完整回放和 `pending` 状态。
8. 网络恢复或重新登录后，记录自动提交；成功响应包含稳定 `server_record_id`，本地状态变为 `synced`。
9. 同一记录连续点击补传、刷新和后台重试，服务端只保留一条记录，所有请求使用同一 `client_record_id`。
10. `401`、`429`、`500`、超时和断网均不删除本地记录；分别进入认证等待或退避重试状态。
11. 明确的回放校验失败显示原因并保留可导出的原始文件；不被无限自动重试。
12. 历史页“检查并补传”能列出并处理旧版本迁移来的未同步记录。
13. 旧记录没有 `speed_eligibility` 时仍可在历史和普通排行榜按原规则显示；不会因迁移被批量隐藏。
14. 一个目标速度被判定无资格时，其他目标、分数、回放和记录可见性不变。

### 6.3 大回放验收

15. 构造超过单请求阈值的 `5×5` 完整回放，客户端自动创建分块任务而非发送必然失败的完整请求。
16. 在任意分块后断网并刷新，继续上传时不重复已确认块，最终得到一条完整服务器记录。
17. 任意块哈希或整体哈希不匹配时，服务端拒绝原子入库，客户端保留证据并显示需处理状态。
18. 小于阈值的 4×4 记录继续走现有单请求路径，回放内容和接口兼容不变。

### 6.4 存储与安全验收

19. IndexedDB 升级失败或浏览器拒绝写入时，用户得到明确导出/重试提示；已经存在的记录不被清空。
20. 访问令牌不再作为长期凭证存放在 `localStorage`；设备 Cookie 无法被页面脚本读取。
21. 服务端仍对手工修改的本地文件执行模式、种子/会话、回放和终局校验。
22. 发布前后排行榜记录数、玩家数和正常历史可见性不得出现未批准的下降；任何下降自动阻断发布。

### 6.5 管理员运维验收

23. 管理后台可按稳定错误码查看服务器已观测的投递结果，并明确声明无法统计从未发出的浏览器本地记录。
24. 管理员可撤销单个或全部设备会话；原始 Cookie/token 不可见，每次操作均写入审计。
25. 记录详情能通过 `client_record_id` 和回放指纹定位幂等结果，并分别显示记录状态、分块状态和目标级资格。
26. 用户自助补传成功后，管理员能在记录详情和审计事件中看到同一 `server_record_id`，无需再人工补录。
27. 迁移/发布只读对账检测到记录、玩家、Top N 或目标榜单数量未批准下降时，发布被阻断且不修改生产数据。
28. 上传失败、缺少新资格字段或单个目标速度异常不会触发整条记录自动隐藏；人工隐藏仍要求明确原因和审计。

## 7. 指标与日志

最小指标集合：

- 终局本地落盘成功率/失败率及浏览器存储错误数；
- `pending → synced` 的中位/95 分位时延；
- 各状态数量和按错误代码分组的重试次数；
- 幂等命中数、重复请求数、分块上传成功率和中断恢复率；
- 会话恢复成功率、明确撤销率、非预期重新登录率；
- 服务器普通记录、排行榜资格和玩家数量的发布前后快照。

日志不得记录密码、完整访问令牌或完整回放；使用用户 ID、客户端记录 ID、回放摘要和结构化错误代码。

## 8. 范围外

- 不重新设计 RPL1 的信息密度或动作编码；本任务只保证现有格式可靠保存和传输。
- 不新增 Service Worker、消息队列、微服务或第三方同步平台。
- 不把 `2048-ranked` 变成账号或记录权威；权威仍是 `2048-game-api`。
- 不自动认定历史速度异常为作弊，不隐藏、删除或批量重写其他玩家成绩。
- 不允许任意上传未经本地历史确认的文件直接获得排行榜资格。
- 不在本阶段改变排行榜排序、计时定义或游戏随机数规则。
- 不把游客记录无提示地归属给登录账号；归属确认是必要的用户操作。
- 不重构管理员后台整体框架，不新建独立“上传中心”顶级模块。
- 不修改 `2048-ranked` 的独立管理页面。
- 不收集或上传浏览器中尚未尝试发送的完整本地历史作为管理员遥测。
- 不提供管理员批量重试全部记录、任意 JSON 直入排行榜或一键批量隐藏工具。

## 9. 实施决策摘要

1. 认证采用“服务端可撤销的长期设备会话 Cookie + 内存短期访问令牌”，复用现有认证/刷新边界，逐步淘汰长期 `localStorage` token。
2. IndexedDB 记录成为唯一可靠发件箱，上传队列只引用记录 ID；复用现有回放验算、唯一索引和 `/api/records`。
3. 所有失败先保留证据，再按错误分类决定自动退避、等待认证或人工处理。
4. 通过历史页提供“检查并补传”，把“本地有记录但服务器未知”变成用户可见、可恢复的状态。
5. 只有超出单请求限制的回放才进入分块上传，避免给普通 4×4 记录引入额外复杂度。
6. 任何资格校验均按目标和记录语义精确处理，不以隐藏数据作为修复手段。
7. 在现有 `2048-next` 管理后台补充投递健康、设备会话、记录诊断、审计和只读对账；不另建后台、不改 `2048-ranked`。

## 10. 需求收敛结论

用户目标、范围、错误处理、兼容策略、手动补传语义和安全边界已确定；无阻塞性产品问题。下一步应按 `design.md` 和 `implement.md` 实施，实施前需要用户明确批准本次最终规划摘要。
