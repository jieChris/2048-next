# 页面视觉基线维护 PRD

## 背景与问题

项目已有可切换页面、设备和主题的 `visual-preview.html`，但目前只有桌面与单一移动尺寸，也没有提交到 Git 的稳定截图基线。页面调整主要由 AI 完成时，单靠人工记忆或临时截图无法确认关键尺寸是否同步更新，移动端溢出、错位和无意义全局元素容易反复出现。

账号设置游客登录页是首个治理对象：共享用户标识曾在页面左上角生成“游客”，与登录表单重复且没有操作价值；发布复核后的可复现范围为 33 个页面状态和 18 个可视弹窗／覆盖层。

## 目标

- 不引入商业工具或新依赖，复用现有预览页、Playwright 和 Git。
- 将关键页面、视口、主题和状态定义为可重复的视觉场景。
- 将批准后的 PNG 基线提交到项目目录，由 Git 历史承担版本追踪。
- 页面视觉发生变化时，要求 AI 同步运行验证；只有确认属于预期变化时才允许显式更新基线和清单。
- 覆盖仓库全部页面和已盘点弹窗，并验证每个场景无横向溢出。
- 账号设置游客登录页额外验证“游客”全局标识不存在、登录表单可见。

## 使用者与用户故事

- 作为维护者，我可以在统一预览页切换 320×568、390×844、768×1024、1280×720 四个关键尺寸，快速检查页面适配。
- 作为提交页面改动的 AI，我能通过固定命令比较批准基线，并在差异属于预期时通过独立命令更新截图。
- 作为代码审查者，我能从 Git diff 和场景清单判断哪些页面、尺寸和主题发生了视觉变化以及变更原因。
- 作为后续维护者，我不需要购买 Figma、Chromatic 或 Percy 才能复现全量视觉验证。

## 产品决策

### 画板与关键尺寸

继续使用项目内 `visual-preview.html` 作为只读画板，不为每个页面和尺寸创建静态 HTML。关键尺寸为：

- 320×568：小屏手机下限。
- 390×844：当前主移动设计尺寸。
- 768×1024：平板与中间断点。
- 1280×720：常见桌面可视区。

### 基线保存与版本

- 批准后的 PNG 保存于 `tests/visual/baselines/` 并提交 Git。
- 失败产生的实际图、差异图、trace 和报告保存在现有已忽略的 `test-results/`、`playwright-report/`，不提交。
- 文件名保持稳定，不生成 `v1`、`v2`、`final` 等副本；图片版本由 Git 提交历史管理。
- `tests/visual/manifest.json` 记录基线标识、页面、状态、尺寸、主题、更新日期和原因。

### 更新规则

- 普通视觉测试失败不得自动覆盖基线。
- 仅在人工或任务目标确认差异为预期后运行独立更新命令。
- 修改页面布局、样式、字体、主题、可见文案或视觉状态时，至少重新验证本次影响的页面与已登记关键场景。
- 更新截图时必须同步更新 manifest 的日期和原因；没有视觉变化时不制造图片提交。
- 当前项目采用全量登记；新增页面或可视弹窗必须加入同一关键尺寸与主题矩阵，除非执行记录明确说明例外原因。

## 当前范围

页面与弹窗固定中文、确定性认证/API/时间/随机状态，覆盖：

- 320×568，浅色与夜间。
- 390×844，浅色与夜间。
- 768×1024，浅色与夜间。
- 1280×720，浅色与夜间。

当前共 408 个视觉场景：

- 33 个页面状态 × 4 个尺寸 × 2 个主题 = 264。
- 18 个弹窗／覆盖层 × 4 个尺寸 × 2 个主题 = 144。

每个场景在截图前断言页面核心状态可见且文档没有横向溢出。账号设置游客页的 8 个场景还同时断言：

- 页面处于游客登录状态。
- `#home-user-display` 不存在。
- 登录表单可见。
- 文档不存在横向溢出。
- 动画和过渡被关闭，语言、主题和本地存储状态已固定。

## 测试决策

- 使用现有 `@playwright/test` 的 `toHaveScreenshot`，不增加依赖。
- 使用独立 Playwright 配置和独立 npm 命令，避免普通 Smoke 意外更新视觉基线。
- 视觉基线只捕获像素回归，不替代现有功能 Smoke、结构关系断言、可访问性和溢出断言。
- 本地交互验收优先使用 Codex 内置浏览器，也允许项目专用的隔离 Chrome 或 Playwright；代理启动的浏览器资源在不再需要后必须自动关闭。

## 不在范围内

- 商业视觉回归平台、云端画板或 Figma 文件。
- 其他语言、真实生产账号数据和 Chromium 之外的浏览器内核。
- 自动接受视觉差异。
- 将失败产物、临时截图或每次运行结果提交 Git。
- 在本轮重构登录、注册或账号业务逻辑。

## 验收标准

- `visual-preview.html` 可切换四个关键尺寸并准确调整 iframe 宽高。
- 仓库提供 `test:visual` 与 `test:visual:update` 两个职责分离的命令。
- 独立视觉测试描述 33 个页面、18 个弹窗的 408 个固定场景，并包含横向溢出断言。
- 账号设置页 8 个场景包含无游客标识和登录表单可见断言。
- 批准基线目录和 manifest 位于 `tests/visual/`，失败产物仍保持忽略。
- `.trellis/spec/visual-validation.md` 与 `AGENTS.md` 明确规定页面视觉改动后的验证和基线更新义务。
- 登录页现有根因修复与移动端布局改动通过类型检查、目标单测/Smoke 的静态检查以及内置浏览器实际验证。
