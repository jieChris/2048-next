## 1. 业务定义与验收口径

### 1.1 竞速指标的唯一含义

对目标方块 `T`：

```text
speed_ms(T) = 从本局第一次有效移动正式启动计时，到第一次合成 T 的累计计时时间
```

因此：

- 2K 竞速不是“上一块合成到 2048 合成”的分段时间；
- 页面刷新或恢复不能把已完成动作重新计时；
- 对局仍在进行时关闭页面所经过的时间是否计入，必须服从当前主计时器合同。当前项目已有明确测试：有排行榜的活动对局在页面关闭期间继续计时，因此恢复后的回放时间轴也必须包含这段时间；
- 同一条回放中，2048、4096、8192 等目标的时间都来自同一累计时间轴；
- `duration_ms`、回放动作累计时间、页面主计时器和各目标方块时间不得各自维护相互矛盾的起点。

### 1.2 完整修复的成功条件

修复完成必须同时满足：

1. 刷新前的 V1 回放内容是刷新后回放的逐字前缀；
2. 前缀中的方向、出生块、`deltaMs`、扩展记录、初始块、起始时间和会话身份不变；
3. 恢复机器耗时不会进入正式回放；
4. 页面关闭期间的计时既不漏计、也不重复计入；
5. 恢复后的下一次真实动作按同一时间轴继续；
6. 2K、4K、8K 等目标互不连坐；
7. 缺少新资格字段的历史记录保持原有可见性，不再默认隐藏；
8. 现有历史记录、回放对象、普通分数和最大方块不被删除或覆盖；
9. 榜单数量、玩家数量或 Top N 发生未批准的大幅下降时，发布自动阻断；
10. 4×4、5×5、斐波那契、八方向、带撤回/特殊出生块等 V1 回放路径不被破坏。

## 3. 根因分析（Break-the-Loop）

### 3.1 根因分类

| 分类 | 本次表现 |
| --- | --- |
| A. 缺少规范 | 没有定义“检查点恢复后，原回放必须保持逐字前缀”以及统一时间轴 |
| B. 跨层契约缺失（主因） | 页面主计时器从 `duration_ms` 恢复，服务端竞速却从回放 `deltaMs` 重算，两者没有一致性合同 |
| C. 变更传播失败 | 为节省存储移除 `ui_state.saved_state` 后，恢复路径从直接状态恢复变成回放 fallback，却没有同步保留 V1 会话 |
| D. 测试覆盖缺口 | Smoke 只验证盘面、分数、种子和 token，没有验证回放前缀、逐步时间和恢复后目标计时 |
| E. 隐式假设 | 误以为用正常 `manager.move()` 重演，只要盘面一致就等价于恢复；实际它还会触发采集器和计时副作用 |

### 3.2 真实故障链

关键路径：

1. `32b8b673` 为降低本地存储占用，把检查点镜像改为：

   ```js
   buildRankedCheckpointPayload(manager, { includeSavedState: false })
   ```

2. 镜像仍保存 `replay_string` 和 `duration_ms`，但没有完整 `ui_state.saved_state`；
3. `parseReplayImportEnvelope()` 解码 V1 时只返回 `replayMoves + replaySpawns`，丢掉原始 `records[].deltaMs`、`startUnixMs` 和扩展记录；
4. `restoreManagerFromRankedCheckpointReplay()` 调用 `restartWithBoard()`，再循环调用正常 `manager.move()` 重建盘面；
5. 正常采集器 `recordSessionReplayV1Move()` 用当前 `Date.now()` 重写每条历史动作的 `deltaMs`；
6. 950 步恢复机器耗时成为 `439ms`；恢复结束后 `last_event_at_ms` 留在当前时刻；
7. 页面主计时器另从检查点 `duration_ms` 恢复，所以 UI 看起来可能正常；
8. 最终服务端从被污染的回放重新累计 `deltaMs`，把 2048 写成 `439ms`。

关键实现位置（实施前须以生产基线重新定位行号）：

- 前端检查点恢复：`js/online_leaderboard_runtime.js` 的 `restoreManagerFromRankedCheckpointReplay()`；
- V1 解析丢时间：`src/bootstrap/game-manager-replay-helpers-runtime.ts` 的 `parseReplayImportEnvelope()`；
- 正常采集重写时间：同文件 `resolveSessionReplayV1DeltaMs()` / `recordSessionReplayV1Move()`；
- 服务端累计目标时间：`src/replay_verify.ts` 的 `verifyReplaySubmission()`；
- 榜单读取目标时间：`src/server/app.ts` 的 `/api/leaderboard?metric=speed`。

### 3.3 为什么第一次修复失败

| 错误做法 | 失败原因 |
| --- | --- |
| 用平均每步 `<20ms` 标记整条记录 `review` | 只识别症状，未修恢复；阈值不能还原真实时间，也不能证明作弊 |
| 查询只读 `speed_eligibility='eligible'` | 把缺少新字段的正常历史全部排除 |
| `0027` 将所有旧标准记录写成 `review` | “未知”被错误解释成“不可信”，且没有审核闭环 |
| 整条记录一个资格 | 2K 异常会连带隐藏同局 4K、8K 等可能正常的目标指标 |
| 先在生产迁移再观察 | 没有榜单快照、数量门禁和自动回滚条件，直接造成榜单只剩一条 |

### 3.4 系统性扩展

同类风险不限于 2K：

- 所有使用 V1 检查点 fallback 的有排行榜模式；
- 4×4、5×5、斐波那契、八方向以及特殊出生块；
- 管理员救援从回放构建 `sessionReplayV1` 的路径；
- 普通完整/精简存档恢复与检查点恢复对页面关闭时间的处理；
- 用户最快速度、速度成就及任何读取 `tile_times_ms` 的查询；
- 第一有效移动的回放锚点与主计时器起点是否一致。

因此修复不能只给 2K 查询加条件，也不能只针对样本记录做数据补丁。

## 4. 统一时间轴与恢复不变量

### 4.1 符号

- `Rcp`：检查点 V1 回放的原始记录序列；
- `Ecp = Σ timedDelta(Rcp)`：检查点回放中 `move/undo` 的累计 `deltaMs`；
- `Dcp`：检查点保存的 `duration_ms`；
- `Trestore`：恢复完成时，主计时器根据现有 server/local anchor 合同得出的累计时长；
- `Tnext`：下一次真实有效动作发生时的主计时器累计时长；
- `Dnext`：下一条正式回放动作的 `deltaMs`。

`ext/checkpoint/end` 没有动作耗时，不计入 `Ecp`。

### 4.2 必须成立的不变量

#### I1：回放根与前缀不变

恢复后的新回放 `Rnew` 必须满足：

```text
root(Rnew) = root(Rcp)
records(Rnew)[0..len(Rcp)) = records(Rcp)
```

“相等”包括全部 V1 记录字节：`dir`、出生索引/值、`deltaMs`、撤回、checkpoint、所有 ext、初始块和 `startUnixMs`。服务端已有 `compareReplayLineage()` 的逐记录比较，应复用其语义，不另造宽松比较器。

#### I2：恢复重演没有正式副作用

恢复内部动作不得触发：

- `recordSessionReplayV1Move/Undo`；
- 正式 `moveHistory` 追加（最终历史从原回放派生/保留）；
- 成就、自动提交、终局提交；
- 检查点保存调度；
- 用户输入统计、声音/动画、弹窗；
- 会话完成/放弃或新局预取。

盘面重演只是纯恢复阶段，恢复完成后再一次性提交状态。

#### I3：同一累计时间轴

对任意目标方块 `T`：

```text
tile_time(T) = 首次合成 T 时的 Σ deltaMs
```

在任意真实动作边界：

```text
Σ replay deltaMs = 主计时器在该动作发生时的累计时长
```

允许的差异只有同一事件循环内取时产生的极小测量误差；实现应使用同一个 `nowMs` 快照消除这类误差，而不是设一个宽松的秒级容差。

#### I4：恢复失败必须 fail closed

若 V1 无法解码、模式/种子/会话身份不符、重演后盘面/分数/步数不符，或 `Dcp < Ecp`，不得继续一局“看起来差不多”的有排行榜对局。保留原检查点和错误码供重试/救援，不清空原始回放，不启动一条伪新局。

### 4.3 恢复后下一步的时间续接规则

这是本修复最容易再次出错的地方。

#### 当前产品语义

已有代码和测试明确要求：活动对局在页面关闭期间继续计时。因此关闭页面不是暂停。

#### 正确公式

恢复时保留 `Rcp` 原样，将回放“已经分配给动作的累计时间”基线设为 `Ecp`；主计时器独立恢复到同一时间轴上的当前值 `Trestore`，两者差值是尚未归属下一条动作的有效时间。下一次真实动作：

```text
Dnext = max(0, Tnext - Ecp)
```

其中 `Tnext` 必须来自主计时器的 server anchor 优先、local anchor fallback 的既有解析函数，而不是单独再用一个裸 `Date.now() - last_event_at_ms` 时间轴。

这个公式自然覆盖三段：

```text
Dnext = (Dcp - Ecp) + 页面关闭期间新增时间 + 恢复后等待时间
```

- `Dcp - Ecp`：最后一个已记录动作到检查点保存之间已经流逝、但尚未归属任何动作的时间；
- 页面关闭期间新增时间：当前产品明确要求计入；
- 恢复后等待：恢复完成到下一次真实输入的时间。

不得把 `last_event_at_ms` 简单设置为 `Date.now()`，否则前两段被漏掉；也不得保留旧本地绝对时间直接相减而脱离主计时器，否则系统时钟变化或 server anchor 会再次制造双时间轴。

#### 初始新局同样要统一

初始新局采用确定规则：第一次有效移动建立计时原点，该动作的 `deltaMs=0`；无效输入既不启动计时，也不产生记录。移动逻辑只取一次事件时间 `nowMs`，同一个 `nowMs` 同时建立主计时器 anchor 和回放累计基线。不能一边声明“第一次有效移动开始计时”，一边从页面或回放对象初始化时累计第一步之前的等待时间。

## 5. 前端最小根因修复

### 5.1 生产基线规则

当前工作区前端分支 `codex/admin-console-rebuild-20260802`（HEAD `b73cab95`）与 `origin/main`（调查时 `e9eb8419`）明显分叉，且当前分支不是可靠生产基线。

实施前必须：

1. 获取实际生产部署的前端提交 SHA；
2. 从该 SHA 新建专用修复分支；
3. 对 API 同样从实际生产提交 `ab53282` 或当时线上 SHA 建分支；
4. 禁止把当前旧前端分支直接合并/强推到生产；
5. 修复 PR 明确列出跨仓兼容顺序。

### 5.2 复用现有 V1 解码结果，不创建新回放格式

不需要 V2 格式、额外依赖或新的回放存储体系。V1 已经包含所需信息。

修改 `parseReplayImportEnvelope()` 的 V1 分支，使恢复调用方可以取得：

- 解码后的完整 V1 root：宽高、`initTiles`、`startUnixMs`；
- 完整 `records`（深拷贝，含 `deltaMs` 与 ext）；
- 为盘面重演生成的 actions/spawns；
- 模式、规则、challenge、seed 等已有元数据。

播放器仍可只消费 actions/spawns；检查点恢复必须消费完整 V1 数据。不要让播放器需求继续决定存档恢复的数据密度。

V1 当前序列化器会根据 `sessionReplayV1` 自动生成 mode/ruleset/challenge/seed/custom-timer/owner 等头部扩展记录，再拼接 `session.records`。因此恢复时不能把 decoded records 整包塞回 `session.records`，否则头部扩展会重复。恢复 helper 必须：

1. 校验内部客户端生成的 V1 是规范顺序；
2. 从已知头部扩展还原 session 元数据；
3. 从 `session.records` 中剔除这些会被序列化器自动生成的头部扩展；
4. 保留 exact-spawn、checkpoint、end 和未知扩展在原动作序列中的位置；
5. 恢复后立即重新序列化，并用现有 lineage 比较确认 `identical`。

无法无损还原的非规范 V1 活动检查点必须 fail closed，不能通过移动或丢弃未知扩展来“修好”。

### 5.3 恢复分成“纯重演”和“会话恢复”两步

#### A. 纯重演

复用当前棋盘引擎和强制出生块能力，按解码动作重建最终状态，但开启专用恢复防护：

- 禁止采集和外部副作用；
- 保留并在 `setup()` 后重新建立恢复标志；
- 支持普通方向、八方向、撤回、exact-spawn 扩展；
- 重演后的盘面、分数、成功移动数、撤回数、出生统计必须与从完整回放派生的预期值一致。

不要为了避开 `manager.move()` 重写一套 2048 引擎；最小安全方案是复用现有核心移动逻辑，但把恢复动作置于明确的副作用屏障内。隔离重演过程中允许维护引擎完成后续步骤所需的临时 `moveHistory`、undo/redo stack 和规则状态；这些临时值不得触发外部副作用，最终值必须由原回放/重演结果一次性提交，而不是被当成一组新用户输入。

#### B. 恢复正式会话

纯重演验证成功后，一次性恢复：

- 原 `sessionReplayV1`：原 `init_tiles`、原 `records`、原 `start_unix_ms` 和身份元数据；
- `moveHistory`、`successfulMoveCount`、`undoUsed`、`spawnValueCounts`；
- 后续操作依赖的 undo/redo stack、方向锁、组合计数和模式专有进度；
- `clientRecordId`、challenge、seed、token；
- 主计时器 anchor/offset；
- 下一条动作的累计回放基线 `Ecp` 与主计时器当前时间的接桥状态。

最后再进行一次 `actuate()` 和必要 UI 更新。任何中途异常都回滚到恢复前快照，并保留检查点。

### 5.4 时间采集改为读取统一累计时间

当前 `resolveSessionReplayV1DeltaMs()` 只认 `session.last_event_at_ms` 的本地绝对时间。实施时应最小化改为：

1. 每次正式动作只取一次 `nowMs`；
2. 用现有主计时器 `resolveTimerElapsedMs(manager, nowMs)` 得到本动作累计时长；
3. `deltaMs = currentElapsedMs - session.recorded_elapsed_ms`；
4. 写入动作后更新 `session.recorded_elapsed_ms = currentElapsedMs`；
5. V1 编码仍只写既有 `deltaMs`，新运行时字段不进入文件格式。

恢复 V1 时：

```text
session.recorded_elapsed_ms = Ecp
```

因此下一次动作自动使用第 4.3 节公式。普通完整存档也应保存/恢复这个运行时基线；旧存档无该字段时用 `Σ records.deltaMs` 派生，不能取 0 或恢复耗时。

### 5.5 检查点负载

保持紧凑镜像，不恢复删除整个 `saved_state` 的优化。现有负载已有：

- `replay_string`：完整逐步记录和时间；
- `duration_ms`：保存时总时长；
- `ui_state`：计时 UI/状态；
- 会话身份字段。

只需让恢复正确消费已有信息。若当前 `ui_state` 没有完整 timer anchor 字段，应仅补齐 `timer_elapsed_offset_ms`、`timer_anchor_local_ms`、`timer_anchor_server_ms`、`timer_started_at_ms` 这些既有字段，不嵌入整份棋盘/撤回栈。

### 5.6 非 V1 旧格式策略

旧 V9/V4/纯动作 JSON 不包含可靠逐步时间，不能伪造竞速时间：

- 可继续用于只读回放播放；
- 可用于不进入竞速指标的普通导入/历史浏览；
- 不得作为有排行榜活动对局的可续写检查点；
- 若遇到活动检查点非 V1，恢复 fail closed 并提供救援/重新开始提示，不把重演机器时间写成正式记录。

### 5.7 上线前已经存在的旧检查点

旧检查点没有新时间合同标记，且其中一部分可能已经由有缺陷的恢复路径重写。不能因无法证明计时就丢掉整局：

1. 优先使用身份匹配、时间更新且包含完整 `session_replay_v1` 的本地完整存档；它可保留原逐步时间；
2. 只有紧凑 V1 时，必须先保持其现有字节不变，不能再用机器耗时重写；
3. 新检查点和最终提交携带轻量 `timing_contract_version: 2`，旧检查点缺失该值时在最终提交记录 `legacy_restore_unattested`；
4. `legacy_restore_unattested` 不阻止本地历史和普通成绩保存；由于旧镜像可能已在升级前被重写，除非能与仍保留原 `session_replay_v1` 的完整本地存档或服务端 V1 前缀逐字匹配，否则不能宣称其速度时间连续；
5. 无法证明时，对该续局最终达到的所有竞速目标写目标级排除，不隐藏记录、普通分数或其他玩家成绩；
6. 该兼容分支只用于部署时已存在的旧检查点，新版本生成的 v2 检查点必须满足第 4 节全部不变量。

`timing_contract_version` 不是新回放格式，也不参与棋盘演算；它只让服务端区分“新客户端承诺并通过统一时间轴校验”和“旧检查点无法证明时间连续”两类提交。

## 6. 服务端防御与目标级计时完整性

### 6.1 区分三个概念

1. `records.status='verified'`：棋盘、规则、种子、分数和终局可重算；
2. `tile_times_ms[T]`：从回放逐步时间派生出的目标累计时间；
3. `speed_metric_exclusions_v1[T]`：目标 `T` 是否有已确认的结构性计时问题。

速度异常不能删除普通成绩，某个目标异常也不能污染其他目标。

### 6.2 取代整条记录级资格

不继续扩张当前 `SpeedEligibility = eligible | review | not_applicable` 作为整条记录的公共门禁。最小兼容方案是在 `verification_summary` 增加一个只表达明确排除项的目标 map：

```json
{
  "speed_metric_exclusions_v1": {
    "2048": {
      "reason": "CHECKPOINT_TIMELINE_REWRITTEN",
      "evidence_version": 1
    }
  }
}
```

语义：

- 字段或某个目标键缺失：沿用历史 `tile_times_ms[T]`，保持可见；
- 某个目标键存在：仅排除这个目标的竞速榜、个人最快和速度成就；
- 不引入没有处理流程的 `review` 状态；
- `20ms/步` 等统计只进入只读审计报告，不自动写 `excluded`。

这既兼容旧数据，也避免为了一个 2K 时间隐藏同局 4K/8K。

阶段 B 开始，新写入的记录不再生成 `speed_eligibility`、`speed_policy_version`、`speed_eligibility_reasons` 三个策略 v1 键。API 对这些键只做迁移期历史双读；若代码仍在产生新键，纠正迁移禁止执行。

### 6.3 服务端结构性校验

新提交的必要硬校验：

- V1 `deltaMs` 是安全非负整数且累计不溢出；
- `tile_times_ms[T] <= duration_ms`；
- 目标时间随目标推进非递减；
- 若终局提交存在该会话最后保存的服务端检查点，则最终回放必须是检查点的 `identical/extends`，不能 `rewind/fork/different_root`；
- 检查点前缀比较必须包含 `deltaMs`，服务端现有 `compareReplayLineage()` 已满足；
- 最终 `duration_ms` 与回放累计动作时间的关系遵守第 4 节时间轴合同。

最后一项需注意：总时长可以晚于最后一个动作，因此不能要求永远严格相等；但在“目标由某动作首次合成”时，该目标时间必须等于该动作边界的累计回放时间。

新前端的终局提交携带 `timing_contract_version: 2`，并用终局动作的同一 `nowMs` 生成 payload `duration_ms`。API 对 v2 提交比较客户端主计时器总时长与 verifier 的回放累计时长：

- 一致：正常派生目标速度；
- 不一致：普通记录仍保存，所有受影响目标写入 `speed_metric_exclusions_v1`，原因 `TIMELINE_TOTAL_MISMATCH`，并报警；
- 棋盘、种子或会话 lineage 不一致：沿用现有完整性拒绝，浏览器本地终局记录和待上传载荷必须保留，不能因 API 拒绝而丢局。

这样可把“速度时间不完整”和“整条游戏不存在”分开，同时避免旧页面在发布窗口内因新硬校验而丢记录。没有 v2 标记的旧提交保持兼容，但不会被客户端声明自动提升可信度。

客户端不得直接提交 `speed_metric_exclusions_v1` 并让 API 原样入库。API 只接受时间合同版本和恢复事实输入，目标排除 map 必须由服务端校验结果生成，避免前后端各写一套状态。

若发生 v2 总时长不一致，保留两份原始证据：现有 `records.duration_ms` 继续使用 verifier 的回放累计值以维持数据库语义，客户端主计时器声明值另存 verification summary/audit。二者都不得用于该记录的速度指标，也不应静默用一个覆盖另一个。

### 6.4 发布后旧客户端的新提交

仅修新前端不能处理发布时仍打开的旧标签。API 配置一个明确的 `timing_contract_v2_enforced_at`（取 API 开始支持 v2 且新前端已经上线后的受控时点），在**签发对局会话时**把 `required_timing_contract_version` 固化到服务端 session/token 上下文：

- `enforced_at` 前已签发且没有版本要求的有限存量会话：不因稍后上传或待上传重试而重新分类，只保留异常审计；
- `enforced_at` 后新签发的会话要求 v2，提交声明并通过 v2 时按 v2 结果处理；
- 要求 v2 的会话收到无 v2 提交时，普通记录和回放仍正常保存，但该记录达到的竞速目标写入 `CLIENT_TIMING_CONTRACT_LEGACY` 排除；
- 客户端升级提示必须说明刷新后即可使用新的竞速计时合同；
- admin/migration/import 等非浏览器会话来源不套用这一前端版本门禁，继续走各自现有来源校验；
- 该门禁是前向兼容保护，不证明 v2 能抵抗恶意伪造。强反作弊不在本次范围。

旧页面继续完成修复前的会话仍按旧合同提交；它一旦重新开局并向服务端申请新会话，就会取得 v2 要求，因而不能无限产生新的无合同速度成绩。极少数长期存量会话若出现结构性异常，只能在证据确认后排除具体目标，不能因会话旧而预先隐藏。

最终提交不能由客户端自行降低 session 要求的合同版本。若配置未设置，系统保持影子校验、不启用前向排除，并在健康检查中明确返回 `timing_contract_enforcement: disabled`；发布门禁不允许把“本应启用但实际未启用”当成功。该规则不批量处理旧数据、不因上传延迟误伤修复前的记录，也不丢失旧客户端完成的整局记录。

### 6.5 服务端检查点作为防回归证据

当前前端已停止云端 checkpoint POST，仅保留本地镜像；因此不能假设每局都有服务端前缀。

发布顺序上可以先修本地恢复并用测试保障，不为了本 Bug 重新引入高频云端写入。若将来恢复云端检查点：

- 服务端已有 lineage 比较可直接作为终局前缀证明；
- 保存频率、存储成本和 5×5 超长局另行设计；
- 本次不新增逐步网络上报或复杂反作弊协议。

### 6.6 查询统一条件

以下三处必须使用同一个目标级排除表达式/已有 SQL helper，禁止复制略有差异的条件：

- 公共竞速榜；
- 用户个人最快速度；
- 速度成就。

概念条件：

```sql
tile_times_ms[T] IS NOT NULL
AND NOT (
  COALESCE(verification_summary->'speed_metric_exclusions_v1', '{}'::jsonb)
  ? $target_tile_text
)
```

“缺失默认可见”只应用在现有基础准入条件之后：`verified`、未删除、`official_v1`、有排行榜对局来源、目标已达到以及公开用户等条件一项都不能放宽。普通分数榜、最大方块、回放读取不读取速度排除 map。

### 6.7 异常检测的边界

`950 步 / 439ms` 足以作为事故定位证据，但速度阈值不是时间恢复算法，也不是作弊判定：

- 可以报警、生成审计候选；
- 不可自动改写 `tile_times_ms`；
- 不可自动隐藏全部历史；
- 不可用阈值推断真正耗时；
- 若没有前缀/其他结构性证据，只能标注“需人工调查”，不能改变公共榜单。

## 7. 历史数据纠错与新前向迁移

### 7.1 原则

已执行的 `0027_speed_eligibility.sql` 不得修改。新增下一号前向迁移（实际编号以实现时仓库最新迁移为准），目标是撤销其错误可见性影响，同时保留审计证据。

### 7.2 迁移前只读审计

先生成并人工批准以下快照，不写数据库：

- 各目标方块的榜单记录数、独立玩家数；
- 全时期/日/周/月 Top N：`rank, record_id, user_id, speed_ms`；
- 个人最快和速度成就受影响数量；
- `speed_eligibility` 各值分布；
- 被 `0027` 修改的 347 条记录清单及其原 `updated_at` 可恢复性；
- 异常样本每步分布与目标级建议处置。

审计输出必须落为版本化 JSON/CSV 工件并带数据库只读快照时间，不能只复制终端文字。

### 7.3 前向纠正迁移

迁移采用以下保守规则：

1. 对当前策略 v1 生成的 record-level `speed_eligibility` 三个键做分类清单；`SPEED_LEGACY_UNCLASSIFIED`、`SPEED_AVERAGE_MOVE_TOO_FAST`、`eligible` 和 `not_applicable` 必须分别统计，出现未知值/原因则事务停止；
2. 移除所有已识别策略 v1 的 `speed_eligibility`、`speed_policy_version`、`speed_eligibility_reasons` 键。`SPEED_AVERAGE_MOVE_TOO_FAST` 只是阈值审计信号，不能继续作为整条记录的公共门禁；已证实异常改用第 4 条目标 map；
3. 不改 `status`、`deleted_at`、回放对象、`tile_times_ms`、分数、最大方块、终局时间；
4. 不把所有记录批量写成 `eligible`；查询通过“历史字段缺失默认可见”兼容；
5. 对已确认异常记录只写有证据的目标键 `speed_metric_exclusions_v1.2048`；同局 4096/8192 继续只读审计，不能因 2048 异常自动连坐，也不能反过来宣称其已经正确；
6. 不覆盖原 verification summary 的其他键；
7. 写入稳定审计事件，记录迁移版本、目标、原因和旧/新摘要哈希；
8. 迁移用 record id、replay hash、目标值和预期 `439ms` 联合 guard；任一证据不符则整个事务失败；
9. 纠正迁移不再次设置 `updated_at`；该字段已被 0027 批量覆盖且没有可靠旧值时，不伪造恢复，审计中明确保留这项不可逆影响。

先在生产快照副本执行并比对，确认只命中预期行数后才能在生产执行。

生产迁移前还必须验证：阶段 B 部署时间之后写入的记录中，策略 v1 三个键新增数量为 0。若不为 0，说明旧写入路径仍活跃，停止迁移并先修代码，不能靠迁移反复清理。

### 7.4 历史成绩恢复验收

- 公开 2K 榜恢复到迁移前合理的玩家/记录规模，而不是只有一条；
- 确认的 `439ms` 仅从 2K 指标排除；
- 该记录的回放、普通分数、最大方块以及其他未证实异常的目标指标仍存在；
- 没有记录被删除、改成 `hidden` 或失去 replay object；
- 若迁移结果命中数不是只读审计预期值，事务回滚。

| 纠正迁移 | 移除审计清单中全部已识别策略 v1 键；除精确目标排除 map 外其他摘要不变 |

### 9.4 内置浏览器 Smoke（硬性）

网页交互验证只能使用 Codex/ChatGPT 内置浏览器，禁止启动独立 Playwright、Chrome、Safari 或其他外部浏览器实例。

真实场景：

1. 用本地 API 建立可继续的排行榜对局；
2. 走若干固定动作并记录 `replay_string`、盘面、分数、主计时器；
3. 等待可控时间后刷新；
4. 核对刷新后立即序列化回放与刷新前 `identical`；
5. 再等待并走一步；
6. 核对旧前缀完全不变，新 `deltaMs` 与主计时器累计一致；
7. 完成一个小型 fixture 对局并提交本地 API；
8. 核对服务端 `tile_times_ms` 与页面目标计时一致；
9. 核对没有重复提交、成就误触发或 checkpoint 被错误清除。

如果内置浏览器不可用，浏览器 Smoke 明确阻塞，不得降级到外部浏览器。

## 10. 发布顺序、门禁与回滚

### 10.1 发布前备份

必须同时取得：

- 数据库一致性备份；
- `records`、`ranked_checkpoints`、`leaderboard_best` 相关表的只读导出；
- 各目标榜单完整 JSON 快照；
- Top N 与玩家数/记录数摘要；
- API/前端当前生产 SHA、迁移版本和健康检查结果。

备份恢复流程必须在生产副本演练，不能只确认“文件存在”。

### 10.2 分阶段发布

1. **阶段 A：测试和只读审计**——不改变查询或数据；
2. **阶段 B：API 安全兼容版本**——上线目标 map、record-level 双读、v2 校验和旧客户端前向保护，但 `timing_contract_v2_enforced_at` 暂不启用；迁移前榜单结果必须保持不变。该版本成为后续发布不可越过的 API 回滚下限；
3. **阶段 C：前端根因修复**——新恢复不再产生污染回放，v2 提交进入 API 影子校验；观察恢复错误率、时间轴一致率和提交成功率；
4. **阶段 D：启用前向时间合同**——在前后端 Smoke 通过后设置 `timing_contract_v2_enforced_at`；旧标签的新提交仍保存普通记录，但不再新增不受证明的速度指标；
5. **阶段 E：生产副本迁移演练**——移除策略 v1 的 record-level 键、写入确认异常目标 map，行数、摘要哈希、榜单 diff 全部通过；
6. **阶段 F：生产前向纠正迁移**——事务内执行；提交瞬间旧历史恢复可见、确认异常目标仍被排除，命中数不符立即回滚；
7. **阶段 G：内置浏览器线上 Smoke + 榜单快照复核**。

双读规则是：目标 map 优先；map 无对应键时，迁移前的非 `eligible` record-level 状态暂时保持旧行为；迁移移除策略 v1 三个键后，字段缺失按历史可见处理。这样先部署 API 不会让 `0.439s` 重新出现，后执行迁移也不会产生空榜窗口。迁移稳定后再在后续普通版本删除只为过渡存在的 record-level 读取，不与本次事故修复同窗口清理。

阶段 B 的兼容版本必须单独打不可变镜像/tag 并完成健康检查。阶段 F 之后，禁止回滚到阶段 B 之前的 `ab53282`：它不认识“缺字段默认可见”和目标排除 map，会重现空榜或错误展示。若必须越过该下限，只能先在事务中执行并验证基于备份生成的补偿迁移，再切换旧代码。

### 10.3 自动阻断门禁

发布工具在变更前后对每个目标比较：

- 公开记录数；
- 独立玩家数；
- Top N 的 record/user/speed；
- 个人最快数量；
- 速度成就候选数量。

以下任一条件自动阻断/回滚：

- 任一榜单从非空变空；
- 玩家数或记录数下降超过批准清单中的目标级排除数；
- 非批准 record_id 离开 Top N；
- 普通分数榜发生任何变化；
- 回放对象数量、记录数量减少；
- 新提交出现 `Dcp < Ecp` 或回放 lineage 冲突率异常上升；
- API 健康检查 SHA 与计划不符。

不要使用随意的百分比容忍大规模下降；本次历史纠错的预期变化是可列举的精确记录集合。

### 10.4 回滚

- 阶段 F 之前，前端可切回上一静态发布；API 已启用的旧客户端保护会保存普通记录并排除新产生的无合同速度指标；
- 阶段 F 之后，前端仍可回滚，但 API 不得低于阶段 B 的安全兼容 tag；
- API 主修复若出现问题，只回滚到阶段 B 的兼容镜像，不能直接回到 `ab53282`；
- 数据纠正迁移必须在单事务内执行。若已提交后才发现问题，保持阶段 B API 在线，使用迁移前导出生成新的补偿迁移，不修改 0027/新迁移历史；
- 只有补偿迁移恢复并验证了旧 record-level 字段后，才允许越过阶段 B 回滚下限；
- 任何回滚都不删除回放，不把成绩批量改为 `review/hidden`。

## 11. 明确禁止的方案

以下做法即使能暂时让 `0.439s` 消失，也不接受：

1. 只在前端把异常值显示为 `—`；
2. 只按 `<20ms/步` 过滤；
3. 把所有旧记录设为 `review`、`hidden` 或删除；
4. 把字段缺失当成不可信；
5. 用整条记录一个资格连带排除多个目标；
6. 根据阈值猜测并回填一个“合理耗时”；
7. 恢复时重新调用正常采集路径生成历史回放；
8. 为此 Bug 新建回放 V2、事件总线、双写表或高频逐步网络上报；
9. 直接在当前分叉旧前端分支上补丁并覆盖生产；
10. 没有生产快照和数量门禁就执行迁移。

## 14. Route Deviation

当前修复设计路线无偏离。文档工作流本身的两项保守偏离（仓库没有模板同步目录、当前分支不是生产基线因此不立即提交）已记录在同目录 `execution-notes.md`，未隐瞒，也未因此修改功能或生产状态。

若实施中出现以下情况，必须选择最保守路径、立即记录在本节并继续：

- 实际生产 SHA 与调查基线不同；
- 生产 schema/迁移编号已变化；
- 无法取得迁移前榜单快照或数据库备份；
- 内置浏览器不可用；
- V1 恢复无法在不改格式的情况下满足前缀不变量；
- 历史异常集合无法用确定证据精确列举；
- 纠正迁移命中数与审计不一致。

保守路径分别是：重新基线/重新审计、停止数据写入、暂停发布、保留旧格式、只恢复历史可见性而暂不隔离不确定指标；绝不以批量隐藏作为兜底。
