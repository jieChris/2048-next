# 页面视觉验证规范

本规范适用于页面布局、样式、主题、字体、可见文案和视觉状态变更。目标是让人和 AI 都能重复验证关键尺寸，而不是保存每次运行产生的临时截图。

## 基线与产物

- 批准的视觉基线保存在 `tests/visual/baselines/` 并提交 Git。
- 场景范围、状态、尺寸、主题、批准日期和原因记录在 `tests/visual/manifest.json`。
- 实际图、差异图、trace、视频和 HTML 报告属于运行产物，只保存在已忽略的 `test-results/`、`playwright-report/`。
- 基线文件名必须稳定；不得创建 `v1`、`v2`、`new`、`final` 等版本副本，历史版本由 Git 保存。

## 页面变更后的强制动作

- 修改页面布局、CSS、主题、字体、可见文案或视觉状态后，必须运行该页面已有的结构/溢出断言，并重新验证 manifest 中登记的受影响场景。
- 普通比较使用 `npm run test:visual`；只有确认差异属于预期设计变更后，才可运行 `npm run test:visual:update`。
- 更新 PNG 时必须同步更新 manifest 的 `updatedAt` 和 `reason`；如果视觉没有变化，不得制造基线提交。
- AI 完成页面改动时，必须在执行记录或交付说明中列出已验证的页面、尺寸、主题和结果。无法生成或更新基线时必须明确记录原因，不得声称已经完成视觉验证。
- 当前项目已登记全部页面与已盘点弹窗。新增页面或可视弹窗必须加入 320×568、390×844、768×1024、1280×720 的浅色与夜间矩阵；确实不适用时必须在 manifest 和执行记录中说明原因。

## 全量矩阵

- 当前批准范围为 33 个页面状态和 18 个弹窗／覆盖层，共 408 张 PNG。
- `tests/visual/account-settings.visual.spec.ts` 维护账号设置游客页 8 个场景；`tests/visual/all-pages.visual.spec.ts` 维护其余 400 个场景。
- 新增入口、弹窗或可见覆盖层时，必须同步更新测试登记、基线 PNG、manifest 数量与 Trellis 执行记录。
- 全量更新只用于首次建基线或用户明确批准的大范围视觉变化；日常页面改动仍优先运行受影响场景，最后以普通比较确认未误改其他基线。

## 场景稳定性

- 场景必须固定语言、主题、认证状态、必要的本地存储和 API Mock。
- 截图前关闭动画、过渡和光标，等待字体、i18n 和页面核心状态就绪。
- 动态时间、随机数据、用户内容和网络结果必须替换为确定 fixture 或从截图区域排除。
- 页面通过 Web Crypto 产生随机状态时必须固定 `crypto.getRandomValues` 或显式重置为指定 UI 状态；只替换 `Math.random` 不足以保证确定性。
- URL 锚点、平滑滚动和 iframe 主题等异步视觉状态必须等待最终可见状态，不得只依赖 `DOMContentLoaded` 或固定延时。
- 优先截取稳定的页面或组件区域；只有整页结构本身是契约时才使用整页截图。

## 断言边界

- 视觉截图不能替代功能、可访问性和布局关系断言。
- 每个视觉场景至少保留与本次风险直接相关的明确断言，例如元素可见、不存在横向溢出、无多余全局标识或关键操作可达。
- 测试失败后禁止自动接受新截图；先判断是产品回归、fixture 漂移还是预期设计变化。

## 本地浏览器生命周期

- 本地页面交互和视觉验收遵守根目录 `AGENTS.md`：优先使用内置浏览器，也可以使用项目专用的隔离 Chrome 或 Playwright 测试实例。
- 不得连接或占用用户已有的浏览器会话。代理启动的窗口、标签、测试上下文、调试端口和进程在验证结束且后续不再需要时必须自动关闭。
- `npm run test:visual` 和 `npm run test:visual:update` 可以在本地隔离 Playwright、CI 或其他固定测试环境运行；更新命令仍须满足预期变更确认和 manifest 更新规则。
